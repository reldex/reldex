# 0003 — Qt ↔ Rust Integration

**Status:** Proposed — acceptance conditional on spike S15 (below)
**Date:** 2026-09-20
**Amended:** 2026-09-20 (pre-acceptance, from building `crates/ffi` in M1.3 — see "Amendment (pre-acceptance): what building the boundary changed"; the status is unchanged and S15 is still the gate)
**Supersedes/resolves:** `ARCHITECTURE.md` §13 item 2 (FFI mechanism), item 3's remaining FFI half (completion marshalling, thread affinity, reentrancy), and item 10 in part (crate layout for the FFI/UI tier).

## Context

`SPEC.md` §11 fixes the adapter path as `QML → QObject/QAbstractItemModel → thin C++ adapter → stable Rust FFI → core`, and `ARCHITECTURE.md` invariants 3 and 4 forbid Qt below the FFI line and business rules above it. ADR-0002 settled the core side: one worker thread per session, blocking driver calls, `Completion<T>` per request, column-oriented `RowBatch`, core-owned `ResultId`/`LobHandle`, and an explicit deferral of "a per-session outbound completion/event queue for the FFI adapter". What remains is *how* C++ talks to Rust.

Binding constraints for this decision: the core must stay Qt-free so Android/iOS reuse it unchanged; the boundary must be small, typed and versioned; millions of rows must reach a `TableView` without one object per row; completions arrive on ~20 worker threads and must be delivered on the Qt main thread; `unsafe` must be fenced into one auditable place; and none of this may add a heavy or immature dependency to the most correctness-critical part of the product.

## Decision

**Adopt a hand-written, stable C ABI in one dedicated crate (`crates/ffi`, package `reldex-ffi`), header generated by `cbindgen`, committed, and verified in CI; consumed by a thin C++/Qt adapter that owns all `QObject`s and `QAbstractTableModel`s.**

### D1 — Boundary shape

```text
QML  ──▶ ReldexApp / SessionController / ResultTableModel   (C++ QObject, ui/adapter)
              │  (all Qt, all main thread)
              ▼
         reldex.h — extern "C", opaque handles, #[repr(C)] PODs
              ▼
         crates/ffi  (reldex-ffi: cdylib + staticlib; the ONLY crate with unsafe)
              ▼
         db-core (SessionRegistry, EventQueue, DatabaseSession) — unchanged, Qt-free
```

Layout recorded here (partially resolving `ARCHITECTURE.md` §13 item 10):

```text
crates/ffi/                  reldex-ffi          cdylib + staticlib, unsafe allowed here only
crates/ffi/include/reldex.h  generated, committed, `cbindgen --verify` in CI
crates/sql-text/             reldex-sql-text     vendor-neutral lexer + statement splitter (§C M2)
ui/CMakeLists.txt            CMake root; drives cargo via Corrosion
ui/adapter/                  thin C++ adapter, compiled as a QML module
ui/app/                      QML, resources, translations
ui/tests/                    C smoke harness (no Qt), QTest, qmltest
```

### D2 — Where `unsafe` lives and how it is fenced

`crates/ffi` is the single exception to the workspace `unsafe_code = "deny"`, taken as a crate-level `#![allow(unsafe_code)]` (cargo rejects overriding `workspace.lints` in a manifest — the precedent and the reasoning are already recorded in `crates/mobile-link-check`). It is fenced by:

- `#![deny(unsafe_op_in_unsafe_fn)]`, `#![warn(clippy::undocumented_unsafe_blocks)]`, `#![deny(clippy::missing_safety_doc)]`; every `unsafe` block carries a `// SAFETY:` comment.
- No business logic: every exported function is *validate arguments → call `db-core` → marshal*. A reviewer must be able to read the whole crate in an hour.
- A `dependency_rules`-style test (mirroring `crates/db-core/tests/dependency_rules.rs`) asserts no other crate gains `unsafe_code` allowance.
- Miri over the crate's Rust-side unit tests (handle registry, string marshalling, event drain); an ASan/UBSan build of the C smoke harness on Linux CI.
- Panic containment: **every** `extern "C"` function body is wrapped in `catch_unwind`; a caught panic becomes `RELDEX_STATUS_PANIC` plus a thread-local last-error. Honest caveat: `oracledb` 26.0.0-beta.3 can abort the process during unwinding (ADR-0002 K6, spike U-4) — this boundary cannot contain that, and the ADR must say so rather than claim safety it does not have.

### D3 — Handles, ownership, lifetimes

| Object | Crossing form | Owner | Released by |
| --- | --- | --- | --- |
| Application hub | `ReldexHub*` opaque | Rust | `reldex_hub_destroy` (last, after all sessions) |
| Session | `uint64_t` `ReldexSessionId` | Rust registry | `reldex_session_close` / `reldex_session_abandon` |
| Result set | `uint64_t` `ReldexResultId` (mirrors core `ResultId`, session-scoped) | Rust | `reldex_result_close`, or session close |
| LOB | `uint64_t` `ReldexLobId` | Rust | `reldex_lob_close`, result close, or session close |
| Fetched batch | `ReldexBatch*` opaque | Rust, handed out by an event | `reldex_batch_release` (adapter must) |
| Error | `ReldexError*` opaque + `ReldexErrorView` | Rust | `reldex_error_free` |

Integer ids rather than pointers wherever the core already has a session-scoped id: a stale or foreign id is *reported* (core already distinguishes "belongs to another session" from "closed", ADR-0002 K8), whereas a stale pointer is undefined behaviour. Pointers are used only where the lifetime is unambiguous and the access is hot (`ReldexBatch*`).

### D4 — Result virtualization: zero-copy where it matters

`RowBatch` is already column-oriented, and `TextColumn`/`BytesColumn` are literally *one contiguous buffer plus a `Vec<usize>` of offsets* — the exact shape a C consumer wants. So:

```c
typedef struct { const uint8_t* ptr; size_t len; } ReldexStr;   /* UTF-8, borrowed */

typedef struct {
  uint32_t struct_size;
  int32_t  kind;                 /* ReldexColumnKind, 0 = unknown */
  const uint64_t* null_bits;     /* bit i of word i/64, LSB-first; borrowed */
  size_t   row_count;
  const uint8_t* data;           /* Text/Bytes: the buffer   */
  const size_t*  offsets;        /* Text/Bytes: row_count+1  */
  const void*    fixed;          /* Number/Timestamp/f64/bool: element array */
  size_t   fixed_stride;
} ReldexColumnView;
```

- **Text, bytes, JSON, and the `Unsupported` text rendering: zero-copy.** One `reldex_batch_column()` call per column per batch gives the adapter pointers; `data(row, col)` is then pointer arithmetic plus `QString::fromUtf8(ptr, len)`. No per-cell FFI call.
- **NUMBER and TIMESTAMP: copy, deliberately.** `Number` is 44 B and `Timestamp` ~24 B; `#[repr(C)]` mirror structs live in `crates/ffi`, so ADR-0002's contract types are not constrained by layout. A visible window is a few thousand cells; the copy is free.
- **Formatting stays in Rust, policy stays in the UI.** C++ must not re-implement 40-digit decimal or the historical mixed calendar. The FFI exposes a *bulk* formatter — `reldex_batch_format_column(batch, col, row_start, row_count, const ReldexFormatOptions*, ReldexTextArena* out)` — where options (decimal separator, grouping, scientific threshold, date pattern, NULL glyph) come from user settings. One call per visible window, not per cell. (ADR-0002 D5 put presentation policy in the UI; this keeps the *policy* there and the *mechanism* in Rust.)
- **Never one QML object per row.** `ResultTableModel : QAbstractTableModel` keeps a small map of `row-range → ReldexBatch*` around the viewport, requests the next batch when the view nears the end of what it holds, and releases batches only when the result is closed (MVP retains the fetched prefix — see §C M5 and the Result-Store ADR it produces). `TableView` + `ReldexTableModel` + a plain `Text` delegate; no `QQmlListProperty`, no JS arrays.
- **Character offsets vs UTF-16.** `SqlPosition` counts Unicode scalars (ADR-0002 S3); `QString` counts UTF-16 units. The FFI exposes `reldex_utf16_offset(ReldexStr text, size_t char_offset)` so the adapter never guesses. Thai is BMP and coincides; the non-BMP text spike S11 already proved corpora where it does not.

### D5 — Threading: wake callback + queued drain

```c
typedef void (*ReldexWakeFn)(void* user_data);
void reldex_hub_set_waker(ReldexHub*, ReldexWakeFn fn, void* user_data);  /* fn=NULL to unregister */
bool reldex_hub_next_event(ReldexHub*, ReldexEvent* out);                 /* non-blocking */
```

Rust calls the waker from a worker thread when the per-hub queue transitions empty → non-empty (edge-triggered, coalesced by an atomic flag). The C++ trampoline does exactly one thing — `QMetaObject::invokeMethod(bridge, &Bridge::drain, Qt::QueuedConnection)` — which is the documented thread-safe way into a Qt event loop. `Bridge::drain()` pulls events until empty **or** a budget is reached (256 events / 4 ms), then re-posts, so a flood never starves rendering.

Rules the adapter must enforce, which the ADR states as contract:

1. The waker **must not block and must not call back into `reldex_*`**. Debug builds set a thread-local guard; any FFI entry from inside a waker returns `RELDEX_STATUS_REENTRANT` instead of deadlocking.
2. `reldex_hub_set_waker(hub, NULL, NULL)` must not return while a wake is in progress — the classic use-after-free when the `Bridge` is destroyed. This is an explicit spike acceptance criterion (S15-K5).
3. All `reldex_*` calls except `reldex_session_request_cancel` are made from the Qt main thread. Cancel is deliberately callable from anywhere and must return promptly (ADR-0002 D2 rule 1); the adapter calls it on the main thread and logs if it exceeds 50 ms.
4. `drain()` is never re-entered; the model never issues FFI calls from inside `data()` other than the pure pointer reads of D4.

### D6 — Error model crossing

```c
typedef struct {
  uint32_t struct_size;
  int32_t  kind;            /* ReldexErrorKind; 0 = RELDEX_ERR_UNKNOWN for a kind this header predates */
  int32_t  session_state;   /* usable / needs_validation / lost */
  bool     retryable, has_native, has_position;
  int32_t  native_code;     /* ORA-00942 -> 942 */
  uint32_t char_offset, line, column;
  ReldexStr message, native_message, cause;   /* borrowed from the ReldexError* */
} ReldexErrorView;
```

`ErrorKind` is `#[non_exhaustive]` in Rust, so the C enum reserves `0` as "unknown" and the adapter must treat unmapped values as unknown rather than assert. Native code, position and the rendered `source` chain all survive the crossing — that is what `SPEC.md` §24.14 and the error pane depend on.

### D7 — ABI versioning

`uint32_t reldex_abi_version(void)` returns `(major << 16) | minor`; `reldex.h` carries `RELDEX_ABI_VERSION` and the adapter refuses to start on a major mismatch. Every non-opaque struct begins with `uint32_t struct_size` so fields can be appended without breaking older callers; every enum reserves `0` for unknown. Because core and UI ship in one binary, this is cheap insurance, not a distribution mechanism — its real value is catching a stale `reldex.h` in a developer's build.

### D8 — Build integration

**CMake drives cargo via Corrosion** (`corrosion-rs`, MIT). Qt's tooling — `qt_add_qml_module`, moc, `windeployqt`, the Android/iOS packaging targets — is CMake-native; inverting that costs far more than one `corrosion_import_crate()`. Corrosion handles target triples, profiles and the platform link libraries Rust's std needs (`ntdll`, `userenv`, `bcrypt` on Windows). Fallback if it misbehaves on a mobile target: a hand-written `add_custom_command` invoking cargo, which is ~30 lines. CI caching: `Swatinem/rust-cache` for cargo, `jurplel/install-qt-action` (aqtinstall) with its own cache for Qt, ccache for C++.

### D9 — Mobile reuse

The same C ABI serves both later mobile targets with no second boundary: iOS links the `staticlib` directly into the app (no embedded framework, no extra code signing); Android loads the `cdylib` from the same process Qt for Android already runs, so **no JNI code of ours is required** — the C++ adapter calls the ABI exactly as on desktop. Spike S6 already proved both artefacts build and link. Lifecycle differences (`Qt::ApplicationState` → `ping`/revalidate per `SPEC.md` §18) live in the adapter, not in the ABI.

### D10 — Testability without a GUI

1. `crates/ffi/tests/*.rs` — Rust tests calling the crate's own `extern "C"` functions against the mock driver.
2. `ui/tests/ffi_smoke` — a plain C program linking the cdylib, driving the mock driver end to end. **No Qt.** Runs on all three desktop CI runners and under ASan/UBSan on Linux.
3. `QAbstractItemModelTester` over `ResultTableModel`; `QTest` for the adapter; `qmltestrunner` for QML — all with `QT_QPA_PLATFORM=offscreen`.
4. Frame-time and memory gates are measured on the dev machine with a real swapchain (offscreen timings are not representative of GPU cost); CI runs the correctness half only.

## Consequences

**Easier.** The core stays Qt-free and unchanged, so mobile reuse is a link step. The boundary is data-shaped and small (~40 functions), so it can be reviewed as a unit. Zero-copy on the dominant column types means the million-row path has no marshalling layer at all. Everything below the ABI is testable without Qt, and CI keeps its fast hermetic Rust job. No new production dependency enters the Rust graph (`cbindgen` is build-time only; Corrosion is CMake-only).

**Harder.** We own memory and lifetime discipline by hand. `unsafe` exists, and an auditable exception to the workspace rule must be maintained. The header is generated output that must be kept honest (`cbindgen --verify` in CI). Every new core capability needs a small, deliberate FFI addition — which is a feature, not a bug, given "keep public APIs small", but it is friction. And the panic story is only as good as the driver: `oracledb`'s abort-on-unwind defect is not containable here.

## Alternatives considered

| Option | Why rejected |
| --- | --- |
| **`cxx-qt` (KDAB)** | Inverts the architecture the spec fixes: Rust code *becomes* the `QObject`, so UI glue migrates into Rust and a Qt build dependency enters the Rust graph. Even isolated in a `reldex-qt` crate, every Rust build then needs Qt headers — including the Android/iOS cross-builds that spike S6 deliberately proved with *no* extra toolchain. It is compile-time coupled, so there is no stable ABI to version, and at its current 0.7-era API maturity it is a moving dependency in the layer `SPEC.md` §2 ranks most critical. Reconsider only if hand-written FFI boilerplate becomes the dominant cost, which the small surface in D3 makes unlikely. |
| **`cxx` (plain)** | Genuinely good ergonomics and it would remove most hand-written marshalling. But it is a source-level bridge, not an ABI: it adds a codegen step to both toolchains, its `Result` → C++ exception mapping is a second error path next to `ReldexError`, and its `UniquePtr`/`rust::Slice` types leak into the adapter, making the adapter thicker rather than thinner. The zero-copy column view of D4 is the shape we actually need and it is trivial in plain C. Net: real cost, little gain, one more dependency in the boundary layer. |
| **UniFFI** | Targets Kotlin/Swift/Python; no first-party C++ backend. Its record/enum marshalling copies everything, which is the opposite of D4. |
| **Rust-side Qt bindings (`qmetaobject-rs`, `ritual`)** | Puts Qt in the core's dependency graph and violates invariant 3 outright. Single-maintainer projects in the most critical layer. |
| **Serialized message protocol (JSON/FlatBuffers over a pipe or shared buffer)** | Exactly the "stringly/tagged cross-layer protocol" `AGENTS.md` warns against, plus a serialization copy on the million-row path. |
| **Skip C++: QML talks to Rust through a generated module** | Not an option under `SPEC.md` §11, and it would put business rules in QML. |

## Evidence/benchmarks

### Spike S15 — what must be proven before this ADR is accepted (1–2 days, `opus`)

Build the thinnest vertical slice that is *the real thing*: real `reldex-ffi`, real cbindgen header, real Corrosion build, real `QAbstractTableModel`, real wake→`invokeMethod` path, mock driver producing 1,000,000 rows of the S14 shape (`NUMBER`, `VARCHAR2(40)`, `DATE`).

**Kill criteria — any one fires and ADR-0003 is re-opened with the owner, exactly as ADR-0001's spikes were:**

| # | Criterion | Threshold |
| --- | --- | --- |
| K1 | Scroll frame time, flick-scrolling the full 1M rows on the dev machine, 100% and 150% DPI | p99 > 16.7 ms, or p50 > 8 ms (`SPEC.md` §19: 60 FPS minimum) |
| K2 | First-row latency, Execute → first row painted, mock driver, in-process | > 150 ms |
| K3 | Retained memory for 1M rows of the S14 shape | > 200 MB RSS growth (≈116 B/row of data; anything far above means the pipeline copies) |
| K4 | Per-batch boundary cost: event delivered → 1,000-row batch described and its columns viewable | > 200 µs; or per-cell `data()` average > 200 ns |
| K5 | Waker teardown: destroy the C++ bridge under a flood of completions, 10,000 iterations, ASan | any use-after-free, race, or hang |
| K6 | UI never stalls: a mock statement blocking for 10 s must not delay any frame or any other session | any frame > 33 ms attributable to the boundary |
| K7 | Build integration: CMake+Corrosion+Qt builds and the offscreen tests pass on windows/ubuntu/macos runners | fails on any of the three, or exceeds a 25-minute cold CI job |

K1/K3 failure with a *diagnosed* cause in the model (not the boundary) is a design fix, not a kill — the kill is "the boundary itself cannot meet it".

As of this writing (2026-09-20) spike S15 has not been run; this ADR's status stays **Proposed** until it is, per the owner-decision facts recorded in `docs/exec-plans/active/phase-1.md` (the owner has not accepted ADR-0003).

## Amendment (pre-acceptance): what building the boundary changed (2026-09-20, task M1.3)

Numbering: `A`. This ADR was written before `crates/ffi` existed. M1.3 built it — the hub, the
session pump, the event queue, the batch views, the bulk formatter, the generated header — against
the mock driver, and the notes below are the places where the implementation and the text above do
not say the same thing. **The status is unchanged: this is still Proposed, and spike S15 is still
the gate.** They are recorded now so that S15 measures the boundary that exists, and so the
acceptance review is not the first time these differences are read.

### A1 — `ReldexColumnView` carries its own bounds (D4)

D4's sketch gives `row_count`, `data`, `offsets`, `fixed` and `fixed_stride`, but no length for any
of the three arrays. A C caller could only derive them — `null_bits` from `row_count`, `offsets`
from `row_count + 1`, `data` from `offsets[row_count]` — and deriving a bound is how an off-by-one
becomes a read past the end of a Rust allocation. The shipped struct adds three fields:

```c
size_t null_word_count;   /* words actually behind null_bits */
size_t data_len;          /* bytes actually behind data      */
size_t fixed_len;         /* elements actually behind fixed  */
```

They cost 24 bytes per column per batch — once per column per fetch, never per cell — and they let
the adapter (and a sanitizer, and a fuzzer) check every access against something the producer wrote
rather than something the consumer computed. `offsets` still has `row_count + 1` entries; that one
is stated in the header rather than given a field, because its length is fixed by the contract
rather than by the data.

### A2 — the element mirrors have no `struct_size`, deliberately (D4, D7)

D7 says "every non-opaque struct begins with `uint32_t struct_size`". `ReldexNumber` and
`ReldexTimestamp` do not, and must not: they are *array elements* behind `ReldexColumnView::fixed`,
so a `struct_size` field would be paid once per cell, and a caller that disagreed about the size
would read a misaligned array rather than a short struct. Their size crosses once per column, in
`fixed_stride`, and the adapter's contract is to check `fixed_stride == sizeof(ReldexNumber)` before
it indexes. D7's rule should be read as *every struct passed by pointer*; structs passed as array
elements version through `fixed_stride` and through the major ABI number.

### A3 — the re-entrancy guard is always on, not debug-only (D5 rule 1)

D5 says "debug builds set a thread-local guard". The implementation sets it in every build. Two
reasons: the guard is one thread-local load and store on a path that already crosses a language
boundary and takes a mutex, so it is not measurable; and the failure it prevents in *release* is the
one that matters — `reldex_hub_set_waker` called from inside a waker asks for a write lock that the
wake itself holds for reading on the same thread, which is a deadlock of the UI thread, not a
diagnostic. A rule that only holds in debug is not a contract. D5 rule 1 should read "every build".

### A4 — `reldex_hub_pending_events` exists, and is not for the adapter

Not in the ADR. `size_t reldex_hub_pending_events(const ReldexHub*)` reports the queue depth without
taking anything from it. It exists because the coalescing property in D5 — a burst of completions
onto an empty queue produces exactly **one** wake — cannot be tested by draining, since draining
re-arms the edge. A test blocks N sessions, releases them, waits for the depth to reach N, and only
then counts wakes. The adapter has no reason to call it: `drain()` should loop on
`reldex_hub_next_event` until it returns false, which is the same information without a race. It is
documented as diagnostic, and S15's K6 instrumentation may use it.

### A5 — the per-session pump is interim, and M2.5 still owns the real queue

ADR-0002 explicitly deferred "a per-session outbound completion/event queue for the FFI adapter"
(its §B2) to the work that is now M2.5. M1.3 needed completions to become events *now*, and had two
options: build the §B2 subset in `db-core`, or pump `Completion<T>` inside `crates/ffi` and leave
§B2 whole for M2.5. **It pumps inside `crates/ffi`**, because the alternative is to design a core
contract from one consumer's needs a milestone before the milestone that owns it, and because
`Completion<T>` is consuming (`poll`/`wait` take `self`), so a core-side queue is a change to how
every existing caller waits — not an addition. The cost is stated plainly: **one extra thread per
open session**, parked in `Completion::wait`, on top of the worker thread `db-core` already runs. At
the ~20 sessions of `SPEC.md` that is ~20 threads that do nothing but block, which is affordable and
is *not* what should ship.

What the pump does, so M2.5 can replace it without renegotiating the ABI:

- Submission stays on the **caller's** thread. `reldex_session_execute` takes the session's slot
  mutex, submits to `db-core`, and hands the resulting `Completion` to the pump under the same
  mutex. Doing the submit on the pump would serialize it behind the previous reply and destroy the
  adapter's ability to have the next fetch in flight while it renders the current batch (K4).
- The slot mutex is what makes ordering exact without a sequence number: `db-core` replies to one
  session strictly in order, so a pump that always waits on the oldest outstanding completion
  produces per-session FIFO by construction.
- Every accepted request produces exactly one event, including one that races a close: after a
  successful close the pump drains what is still queued and answers each one.
- Nothing polls. Every pump thread is *blocked* in `Completion::wait`; there is no sleep interval
  anywhere on the completion path (the only spins in the crate are in test code, waiting for a
  condition the test itself creates).

**What M2.5 must decide, and what this does not decide for it:** whether the queue lives per session
or per hub; whether it is bounded, and what back-pressure means when it is full; whether `Completion`
grows a non-consuming `poll_ref` or is replaced by a channel; and whether events carry a core-side
sequence number (the FFI's ordering argument above rests on the slot mutex, which a core queue would
make unnecessary rather than inherit). The C ABI is unaffected by any of those choices: the adapter
sees `reldex_hub_next_event` either way.

### A6 — `db-core` gained one field: `ExecuteOutcome::columns`

A grid needs column *names* before it has a row. `db-core`'s `Cursor` never leaves its worker thread
and `FetchedBatch` carries only storage kinds, so there was no path by which a caller could learn
them. `ExecuteOutcome` gained `columns: Vec<ColumnMetadata>` (empty for a statement with no result
set), captured through the same panic-containing `call` helper as every other driver call, and
`ColumnMetadata` is re-exported from `db-core`. Additive, no existing behaviour changed, and it is
the right home regardless of what M2.5 does to the queue.

### A7 — D3's names, and what is not there yet

D3's table names `reldex_session_abandon`, `reldex_result_close` and `reldex_lob_close`. The shipped
names are `reldex_session_close_result` (session-scoped, because the id is) and
`reldex_session_close(hub, session, request, disposition)`, which covers both "close" and ADR-0002's
`CloseDisposition` ladder — there is no separate `abandon`, because a close that needs a decision
reports `RELDEX_CLOSE_OUTCOME_DECISION_REQUIRED` and leaves the session open, which is the behaviour
D3's two names were reaching for. **LOBs do not cross yet**: `ReldexLobId` is not in the header, and
a LOB column reports its kind without a handle. That is M1.8/M2 work, and it is a gap, not a
decision.

### A8 — the mock driver is a default cargo feature

`reldex-ffi` has one feature, `mock-driver`, on by default; it links `reldex-driver-mock`, the only
driver the boundary can currently open a session against. This is how M1.3 and S15 drive the
boundary with no database.

The rule this establishes, and the one M1.8 must keep: **a cargo feature never changes the ABI.**
The exported symbol list and the generated header are identical with and without the feature, so one
`reldex.h` describes every build and the adapter is never compiled against a different boundary than
the one it was tested on. What a feature changes is *behaviour*: with `--no-default-features`
(verified to compile and to be clippy-clean) `reldex_hub_open_session` reports
`RELDEX_STATUS_INVALID_ARGUMENT` because there is no driver, and `reldex_mock_release_block` does
nothing. A shipping build should have exactly that shape until a real driver feature replaces the
mock as the default.

### A9 — Miri was not run

D2 lists "Miri over the crate's Rust-side unit tests". Miri needs a nightly toolchain and only
stable is installed here, so this was **not** run and no claim is made about it. What should be run
when a nightly is available, in the order of what it would actually catch:

```bash
cargo +nightly miri test -p reldex-ffi --lib                  # struct_size read/write, strings, arena
cargo +nightly miri test -p reldex-ffi --test lifecycle       # null/unaligned/undersized arguments
MIRIFLAGS="-Zmiri-strict-provenance" cargo +nightly miri test -p reldex-ffi --lib
```

The integration tests that open sessions spawn threads and block on them; Miri runs those, but
slowly, so `--lib` and `lifecycle` are the ones worth the wall-clock. The ASan/UBSan half of D2 is
unchanged and belongs with the C smoke harness (M1.6), where `RELDEX_FFI_WAKER_ITERATIONS=10000`
drives K5.
